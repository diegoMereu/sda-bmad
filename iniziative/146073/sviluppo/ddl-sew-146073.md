## 1. Database

**[FATTO] Informix.** I tre moduli hanno nel `.classpath` il driver `ifxjdbc.jar` / `ifxtools.jar`
`IFXDriver_3.70.JC7X1`. Il SQL è dialetto Informix:
- `systables`, `NVL`, `FIRST n`, `current`, `SYSMASTER:'informix'.SYSDUAL` nei MERGE;
- sequence lette con `… .NEXTVAL FROM systables WHERE tabid = 1`;
- gestione dell'errore Informix "physical-order read".

La connessione la apre `sdaKafkaLibrary` (`SdaConsumer` e `SdaProducer`, `getDBConnection()`) con i
parametri del file di properties esterno al repo. Nel codice non ci sono URL né credenziali.

Non è il PostgreSQL di [contesto/ambienti.md](../../../contesto/ambienti.md) (`ce_cen`,
`ce_eud_api_in`). Istanze, database e utenti Informix di svil e collaudo vanno chiesti (domanda 1).

## 2. Scelte

| Scelta | Motivo |
|---|---|
| Colonne **nullable, senza default** | R-05: i messaggi storici e le spedizioni non USA non hanno i campi. Il consumer SDA scrive `NULL`, non `" "` (SEW-05) |
| `account_key VARCHAR(52)` | lunghezza fissata dalla descrizione del cliente (52) |
| `declaration_id VARCHAR(64)` | lunghezza non definita (arriva da Zonos in fase 2). **[ASSUNTO SEW-03]** |
| `product_id VARCHAR(255)` | da 1 a 255 caratteri. 255 è anche il massimo di `VARCHAR` in Informix. La lunghezza è in **byte**: con un database in locale multibyte (UTF-8) un Product ID non ASCII di 255 caratteri non ci starebbe. Lato Poste non succede, perché `cleanString` toglie i non ASCII (SWP-08); lato SDA sì (domanda 3) |
| `product_id` nella tabella **per articolo** | R-04: il Product ID non si appiattisce sulla spedizione (SWP-02, SEW-02) |
| Nomi minuscoli | come le colonne esistenti; Informix non distingue maiuscole e minuscole nei nomi |
| Niente `COMMENT ON` | Informix non lo supporta: il significato delle colonne sta in questo documento |

## 4. Script

Si eseguono come proprietario delle tabelle, sul database SEW dell'ambiente. `ALTER TABLE … ADD`
**non si può rieseguire**: Informix non ha `ADD COLUMN IF NOT EXISTS`. Prima si controlla (script 0).

### Script 0 — Verifica (prima e dopo)

```sql
SELECT t.tabname, c.colname, c.coltype, c.collength
  FROM systables t, syscolumns c
 WHERE t.tabid = c.tabid
   AND t.tabname IN ('sew_spedizioni_work', 'sew_spedizioni_work_2',
                     'sew_spedizioni_poste', 'sew_spedizioni_poste_inter', '<tabella_inter_scarto>')
   AND c.colname IN ('account_key', 'declaration_id', 'product_id')
 ORDER BY 1, 2;
```

Prima: nessuna riga. Dopo: le righe della tabella della sezione 3.

### Script 1 — `sew_spedizioni_work` (int. 07)

```sql
ALTER TABLE sew_spedizioni_work
  ADD (account_key    VARCHAR(52),
       declaration_id VARCHAR(64));
```

### Script 2 — `sew_spedizioni_work_2` (int. 07)

```sql
ALTER TABLE sew_spedizioni_work_2
  ADD (account_key    VARCHAR(52),
       declaration_id VARCHAR(64));
```

### Script 3 — `sew_spedizioni_poste` (int. 08)

```sql
ALTER TABLE sew_spedizioni_poste
  ADD (account_key    VARCHAR(52),
       declaration_id VARCHAR(64));
```

### Script 4 — articoli Poste (int. 08)

```sql
ALTER TABLE sew_spedizioni_poste_inter
  ADD (product_id VARCHAR(255));

-- nome dalla property kafka.tabella.interscarto dell'ambiente
ALTER TABLE <tabella_inter_scarto>
  ADD (product_id VARCHAR(255));
```

### Script 5 — opzionale: articoli SDA (int. 07, variante B, solo su conferma di Poste)

```sql
CREATE TABLE IF NOT EXISTS sew_spedizioni_work_art (
    id_ldv      VARCHAR(35)  NOT NULL,   -- stessa lunghezza di sew_spedizioni_work.id_ldv: da allineare
    posizione   VARCHAR(10)  NOT NULL,   -- spedizione[].collo[].articolo[].posizione
    product_id  VARCHAR(255),
    data_ins    DATETIME YEAR TO SECOND DEFAULT CURRENT YEAR TO SECOND NOT NULL,
    PRIMARY KEY (id_ldv, posizione) CONSTRAINT pk_sew_sped_work_art
);
```

La chiave `(id_ldv, posizione)` rende idempotente il reinvio dello stesso messaggio, come il duplicato
gestito oggi sulla work. Se serve anche per `sew_spedizioni_work_2`, si crea `sew_spedizioni_work_2_art`
con la stessa struttura.

### Rollback

Prima si riporta il codice alla versione precedente, poi:

```sql
ALTER TABLE sew_spedizioni_work         DROP (account_key, declaration_id);
ALTER TABLE sew_spedizioni_work_2       DROP (account_key, declaration_id);
ALTER TABLE sew_spedizioni_poste        DROP (account_key, declaration_id);
ALTER TABLE sew_spedizioni_poste_inter  DROP (product_id);
ALTER TABLE <tabella_inter_scarto>      DROP (product_id);
DROP TABLE IF EXISTS sew_spedizioni_work_art;   -- solo se creata
```

## 5. Esecuzione

- **Chi**: il DBA ([contesto/ambienti.md](../../../contesto/ambienti.md), AS-04). Per l'Informix SDA il
  referente va confermato (domanda 2).
- **Ordine**: DDL in svil, poi collaudo, poi produzione; **sempre prima** del rilascio del codice
  nell'ambiente. È obbligatorio per `consumer-sew_sped`, che elenca le colonne nell'insert in modo
  statico: senza DDL ogni insert su work fallisce e il record viene saltato dopo i retry.
- **Lock**: `ALTER TABLE` prende un lock esclusivo sulla tabella. Con colonne nullable in coda e senza
  default Informix di norma fa un *in-place alter*, cioè veloce e senza riscrivere le righe. Durante
  l'esecuzione conviene:
  - fermare `consumer-sew_sped` e `consumer-sew_sped_poste`. Gli offset Kafka si committano solo dopo
    il commit sul DB, quindi alla ripartenza il lag si recupera senza perdite;
  - evitare che parta `producer-sew-sped`.
- **Verifica**: script 0 dopo l'esecuzione; poi i test TC-01 dei tre funzionali.
