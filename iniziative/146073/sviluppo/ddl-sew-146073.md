## 1. Database

**[FATTO] Informix.** I tre moduli hanno nel `.classpath` il driver `ifxjdbc.jar` / `ifxtools.jar`
`IFXDriver_3.70.JC7X1`. Il SQL è dialetto Informix:
- `systables`, `NVL`, `FIRST n`, `current`, `SYSMASTER:'informix'.SYSDUAL` nei MERGE;
- sequence lette con `… .NEXTVAL FROM systables WHERE tabid = 1`;
- gestione dell'errore Informix "physical-order read".

La connessione la apre `sdaKafkaLibrary` (`SdaConsumer` e `SdaProducer`, `getDBConnection()`) con i
parametri del file di properties esterno al repo. Nel codice non ci sono URL né credenziali.

Non è il PostgreSQL di [contesto/ambienti.md](../../../contesto/ambienti.md) (`ce_cen`,
`ce_eud_api_in`). Istanze, database e utenti Informix di svil e collaudo vanno chiesti (domanda 1).

## 2. Scelte

| Scelta | Motivo |
|---|---|
| Colonne con **default `''`** [DECISO, Diego 23-11] | i messaggi storici e le spedizioni non USA non hanno i campi (R-05). I consumer mettono le colonne nello statement **solo se il campo arriva valorizzato**; altrimenti la colonna prende il default |
| `zonos_account_key char(52) default ''` | lunghezza fissata dalla descrizione del cliente (esattamente 52) |
| `zonos_declaration_id char(13) default ''` | 13 caratteri. In fase 1 è solo predisposto |
| `zonos_product_id char(255) default ''` | da 1 a 255 caratteri. `char` completa con spazi a destra: chi legge toglie gli spazi finali. La lunghezza è in **byte**: con un database in locale multibyte (UTF-8) un Product ID non ASCII di 255 caratteri non ci starebbe. Lato Poste non succede, perché `cleanString` toglie i non ASCII (SWP-08); lato SDA sì (domanda 3) |
| `zonos_product_id` nella tabella **per articolo** | R-04: il Product ID non si appiattisce sulla spedizione (SWP-02, SEW-02) |
| Nomi `zonos_*`, minuscoli [DECISO, Diego 24-11] | uguali ai campi del tracciato; Informix non distingue maiuscole e minuscole nei nomi (nel codice Poste compaiono maiuscoli) |
| Niente `COMMENT ON` | Informix non lo supporta: il significato delle colonne sta in questo documento |

## 4. Script

Si eseguono come proprietario delle tabelle, sul database SEW dell'ambiente. `ALTER TABLE … ADD`
**non si può rieseguire**: Informix non ha `ADD COLUMN IF NOT EXISTS`. Prima si controlla (script 0).

### Script 0 — Verifica (prima e dopo)

```sql
SELECT t.tabname, c.colname, c.coltype, c.collength
  FROM systables t, syscolumns c
 WHERE t.tabid = c.tabid
   AND t.tabname IN ('sew_spedizioni_work',
                     'sew_spedizioni_poste', 'sew_spedizioni_poste_inter', '<tabella_inter_scarto>')
   AND c.colname IN ('zonos_account_key', 'zonos_declaration_id', 'zonos_product_id')
 ORDER BY 1, 2;
```

Prima: nessuna riga. Dopo: le righe della tabella della sezione 3.

### Script 5 — opzionale: articoli SDA (int. 07, variante B, solo su conferma di Poste)

```sql
CREATE TABLE IF NOT EXISTS sew_spedizioni_work_art (
    id_ldv      VARCHAR(35)  NOT NULL,   -- stessa lunghezza di sew_spedizioni_work.id_ldv: da allineare
    posizione   VARCHAR(10)  NOT NULL,   -- spedizione[].collo[].articolo[].posizione
    zonos_product_id CHAR(255) DEFAULT '',
    data_ins    DATETIME YEAR TO SECOND DEFAULT CURRENT YEAR TO SECOND NOT NULL,
    PRIMARY KEY (id_ldv, posizione) CONSTRAINT pk_sew_sped_work_art
);
```

La chiave `(id_ldv, posizione)` rende idempotente il reinvio dello stesso messaggio, come il duplicato
gestito oggi sulla work. Come le colonne di testata, vale solo per `sew_spedizioni_work`.

### Rollback

Prima si riporta il codice alla versione precedente, poi:

```sql
ALTER TABLE sew_spedizioni_work         DROP (zonos_account_key, zonos_declaration_id);
ALTER TABLE sew_spedizioni_poste        DROP (zonos_account_key, zonos_declaration_id);
ALTER TABLE sew_spedizioni_poste_inter  DROP (zonos_product_id);
ALTER TABLE <tabella_inter_scarto>      DROP (zonos_product_id);
DROP TABLE IF EXISTS sew_spedizioni_work_art;   -- solo se creata
```

## 5. Esecuzione

- **Chi**: il DBA ([contesto/ambienti.md](../../../contesto/ambienti.md), AS-04). Per l'Informix SDA il
  referente va confermato (domanda 2).
- **Cosa**: lato SDA solo lo script 1, su `sew_spedizioni_work` (Diego, 24-11).
- **Ordine**: DDL in svil, poi collaudo, poi produzione. I consumer aggiungono le colonne allo
  statement solo se i campi arrivano valorizzati, quindi il codice si può rilasciare anche prima della
  DDL. La DDL va però eseguita **prima** che il builder mandi i campi (e che `ce-dichiarato-ldv` accenda la
  regola): un insert con le colonne nuove su una tabella che non le ha fallisce e il record viene
  saltato dopo i retry. Gli script 3 e 4 (Poste) servono solo quando parte il punto 2 della fase 1.
- **Lock**: `ALTER TABLE` prende un lock esclusivo sulla tabella. Con colonne aggiunte in coda Informix
  di norma fa un *in-place alter*, cioè veloce e senza riscrivere le righe; il DBA verifica che valga
  anche con il `DEFAULT ''` sulla versione installata. Durante
  l'esecuzione conviene:
  - fermare `consumer-sew_sped` e `consumer-sew_sped_poste`. Gli offset Kafka si committano solo dopo
    il commit sul DB, quindi alla ripartenza il lag si recupera senza perdite;
  - evitare che parta `producer-sew-sped`.
- **Verifica**: script 0 dopo l'esecuzione; poi i test TC-01 dei tre funzionali.
